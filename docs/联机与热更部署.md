## 一点五、域名与 HTTPS（2026-11-04 实装，B 方案）

**为什么是这个方案**：客户端热更地址写死 `http://49.233.138.141/update/...`，
如果让 80 全局跳 443，老客户端全部更新失败。所以三条并存：

| 入口 | 行为 |
|---|---|
| `https://xshy.top` / `https://www.xshy.top` | 200，Let's Encrypt 证书，自动续期 |
| `http://xshy.top` | **308 → https**（域名入口必须加密） |
| `http://49.233.138.141` | **200 不跳转**（老客户端热更通道，不许动） |

**配置**：仓库 `deploy/Caddyfile`（唯一真相源），部署到 `/etc/caddy/Caddyfile`。
关键点：
- 处理逻辑抽成 snippet `(eve_site)`，IP 站与域名站 `import` 同一份，避免两边配飘
- 全局 `auto_https disable_redirects` —— 不让 Caddy 自动给所有站点插 80→443 跳转，
  否则它会连 IP 入口一起跳，热更全挂
- 跳转只写在 `:80` 里，靠 `@domain host xshy.top www.xshy.top` 精确命中

**防火墙**（腾讯云轻量，`describe_firewall_rules`）：80/TCP、443/TCP、443/UDP（HTTP/3）、
22/TCP、27100/UDP、ICMP。

**验收命令**：

```bash
curl -sI https://xshy.top/ | head -3                     # 200
curl -sI https://www.xshy.top/ | head -3                 # 200
curl -sI http://xshy.top/ | grep -i location             # 308 → https
curl -s -o /dev/null -w '%{http_code}' http://49.233.138.141/   # 200，且没有 Location
```

⚠️ **签发过程中的坑**：Caddy 给 `xshy.top` 和 `www.xshy.top` 分别下证书，
先签完的那个能用、另一个那几十秒里会 `curl 000`，不是配错，等 30 秒重测即可。

⚠️ **这台机器上 `raw.githubusercontent.com` 会间歇性超时**（2026-11-04 实测两次失败）。
拉配置文件一律改走 `https://gh-proxy.com/https://raw.githubusercontent.com/<owner>/<repo>/<sha>/<path>`。

### 网页版（WebSocket）中继

浏览器没有 UDP socket，`eve_relay_server.js` 那条路在网页上根本走不通
（详见 `docs/网页试玩版-构建与部署.md` 坑 7）。网页版单独跑一个 WS 中继：

```
/opt/eve-relay/ws_relay_server.js         # 零依赖手写 WebSocket，单文件
/etc/systemd/system/eve-ws-relay.service  # 常驻 + 开机自启 + 崩溃自动重启
/var/log/eve-ws-relay.log                 # 每 60 秒一行统计 + 房间进出日志
```

- 只监听 `127.0.0.1:27101`，**对外只有 443 一个入口**，
  由 Caddy 把它反代成 `wss://xshy.top/relay`（`deploy/Caddyfile` 里的 `@relay`）。
  ⇒ **不需要为它加任何防火墙规则**。
- 客户端（`scripts/net/eve_ws_transport.gd`）默认连 `wss://xshy.top/relay`。
  调试时可以用页面参数临时指向本机，不用重打包：
  `https://xshy.top/play/?relay=ws://127.0.0.1:27101/relay`

```bash
systemctl status eve-ws-relay
systemctl restart eve-ws-relay
tail -f /var/log/eve-ws-relay.log
curl -s http://127.0.0.1:27101/          # 探活：返回 rooms=/conns=/relayed=
node tools/relay/ws_relay_test.js 443 xshy.top wss   # 公网全链路自检（8 条断言）
```

⚠️ Caddy 的 `servers.timeouts.idle` 会掐掉空闲 WebSocket。现设 120 秒，
中继每 30 秒发一帧 ping 保活 —— 改配置时**不要**把 idle 调回几十秒。

## 三、热更（增量）

### 为什么是"增量"而不是全量 pck

| | 全量 pck | **增量 pck（现在这套）** |
|---|---|---|
| 内容 | 所有资源 | **仅 `scripts/` + `data/`** |
| 体积 | **320 MB** | **6.0 MB** |
| 玩家下载（4M 带宽） | ~11 分钟/人，并发直接打满 | ~12 秒 |

`assets/` 占 304 MB 且已经定稿，日常更新全是逻辑和数值 ⇒ 增量包天然只有几 MB。

**代价（必须记住）：**

- **改美术资源无法热更**（贴图 / 音频 / 模型）⇒ 那种更新只能重发整包到群里
- **删文件不生效**：`load_resource_pack` 是**叠加**语义，旧包里的文件还在。
  只要没被引用就没影响，但别指望"删掉某个脚本"能通过热更生效
- 引擎本体（exe / Android 的 libgodot）永远不能热更

### 架构

```
本机                          GitHub Release              服务器              玩家
────────────────────────────────────────────────────────────────────────────────
publish_hotfix.sh
  └─ 导出 6MB pck ──────────▶ hotfix-<版本>
                              6MB asset
                                   │
                                   └── wget ──────▶ /var/www/eve/update/pck/
                                                          │
                              build/version.json ────────▶ /var/www/eve/update/
                                                          │
                                                    ◀── HTTP ── 客户端启动时
                                                               比对 code
                                                               下载 + SHA256 校验
                                                               load_resource_pack
                                                               提示「重启生效」
```

### 目录结构

```
/var/www/eve/
├── index.html                          # 占位页
└── update/
    ├── version.json                    # 版本清单（客户端唯一入口）
    └── pck/
        └── EVE-hotfix-0.14.10.pck      # 增量包
```

### version.json 格式

```json
{
  "version": "0.14.10",
  "code": 18,
  "pck": {
    "url": "http://49.233.138.141/update/pck/EVE-hotfix-0.14.10.pck",
    "size": 6012584,
    "sha256": "dbf6818b…"
  },
  "relay": "49.233.138.141:27100"

```

`code` 是**唯一的比较依据**（比字符串版本号可靠）。客户端：

```
remote.code > local.code  ⇒ 下载
remote.code <= local.code ⇒ 不动作
```

### 发布一次热更的完整步骤

**版本号怎么起**（2026-10-30 定）：

| 改动性质 | 版本号 | 例 |
|---|---|---|
| 小修 / 数值 / 界面微调（走热更） | **四位补丁号**，主版本不动 | `0.14.10` → `0.14.10.1` → `0.14.10.2` |
| 要重发整包（换美术资源 / 换引擎 / 大版本） | 进主版本位 | `0.14.10.x` → `0.14.11` |

`code` 与版本号**相互独立**，永远 +1，跟版本字符串怎么起没关系
（玩家靠 code 判断要不要更，靠 version 只是给人看）。

```bash
# 1. 本机：改版本号 + 一条命令打包上传
#    project.godot:        config/version="0.14.10.2"    ← 小更新用四位
#    export_presets.cfg:   version/code=22               ← ⚠️ 只许递增
#                          version/name="0.14.10.2"
#                          application/file_version / product_version 同步（必须 4 段）
#    ⚠️ project.godot 的 config/version 与 presets 的 version/name **是两处，容易漏一处**
#       （b22 发版时就发现 project.godot 还停在 0.14.10）—— 打包脚本从 project.godot 读 VER，
#       漏改会让包内 build_info 与文件名不一致。
tools/publish_hotfix.sh        # 导出 → 剥 icudt → SHA256 → 推 GitHub Release → 写 build/version.json

# 2. 服务器：拉包（走 ghfast.top）+ 对 SHA256
wget -O /var/www/eve/update/pck/EVE-hotfix-0.14.10.2-b22.pck \
  'https://ghfast.top/https://github.com/xshynews/EVE-AutoChess/releases/download/hotfix-0.14.10.2-b22/EVE-hotfix-0.14.10.2-b22.pck'
sha256sum /var/www/eve/update/pck/EVE-hotfix-0.14.10.2-b22.pck   # 必须和本地一致

# 3. 换清单 /var/www/eve/update/version.json
#    ⚠️ execute_command 有长度限制：整份 JSON 一次塞进去会 AccessDeny，
#    要 base64 切成两段 printf 拼接：
#      printf %s '<前 370 字符>' > /tmp/b64a
#      printf %s '<后段>'      >> /tmp/b64a
#      base64 -d /tmp/b64a > /var/www/eve/update/version.json

# 4. 验收（本机 curl，别只在服务器上自测）
curl -s -o /dev/null -w '%{http_code} %{size_download} %{time_total}\n' \
  http://49.233.138.141/update/pck/EVE-hotfix-0.14.10.2-b22.pck
#    期望 200 / 包大小 / 2~3 秒
```

### ⚠️⚠️ 两条必须记住的规则

**① `code` 是唯一比较依据，且只许递增。**

```
remote.code >  local.code  ⇒ 下载
remote.code <= local.code  ⇒ 不动作
```

`local.code` 来自 `res://build_info.json`（已挂载 pck 时读的是 pck 里那份）。
⇒ 热更一次，玩家本地的 code 就永久 +1，下次必须发更大的 code。

**血的教训（2026-10-30）**：服务器上曾有一份 `code=19`、版本 `0.14.10` 的清单，
而客户端也是 code 19 ⇒ 相等 ⇒ 永远不更，**那份清单是死的，谁都不知道**。
发之前一定先看清单的 code 是不是真的大于客户端。

**② 包必须 ≤ 8MB，最好 ≤ 1.5MB。**

原因不是"省流量"，是**已发出去的老客户端下载超时只有 6 秒**（拆成
15s/300s 是后来才改的，没进已经发给玩家的 APK）。4Mbps 出网 ≈ 500KB/s：

| 包大小 | 下载耗时 | 老客户端 6 秒超时 |
|---|---|---|
| 6.0 MB（未剥 icudt） | 12 秒 | ❌ 每次下到一半被自己砍断 |
| **1.02 MB（剥后实测）** | **2.2 秒** | ✅ |

### 为什么 6MB 里有 4.58MB 是白发

`icudt_godot.dat`（4.575MB）和 `icon.png`（81KB）是 **Godot 导出时强制追加**的，
把名字写进 `exclude_filter` 完全无效（实测照打）。
但它们随 APK/EXE 一起发过，玩家 `res://` 里本来就有 —— `load_resource_pack`
是**叠加**语义，pck 里不放照样能用。

⇒ `tools/pck_strip.py` 在导出后把它们剥掉：**5.68MB → 1.02MB**。
`publish_hotfix.sh` 已内置这一步，不用手工跑。

自查包内容：`python tools/pck_ls.py <pck>` 会按顶层目录和单文件体积排序，
一眼就能看出是不是又把 assets / icudt 打进去了。

### pck 格式的坑（写 pck_strip.py 时踩的，Godot 4.7 / pack_version=4）

```
off 0   4   "GDPC"
off 4   4   pack_version (4)
off 8   12  ver_major / ver_minor / ver_rev
off 20  4   pack_flags
off 24  8   file_base           (u64 = 112，数据区起点)
off 32  8   dir_offset          (u64，目录表起点)
off 40  72  预留
```

⚠️ **头部没有 `file_count`** —— count 在 `dir_offset` 处（u32），别在头部找。

⚠️⚠️ **目录项里的 offset 是「相对 file_base」的，不是文件绝对偏移。**
第一版按绝对偏移切片 ⇒ 每个文件错位 112 字节 ⇒ `project.binary` 里的字符串
被截断 ⇒ 以 `--main-pack` 启动直接 SIGILL 崩溃。

定位办法（不靠猜）：目录项自带 16 字节 md5，两种解释各算一遍 ——
**261/261 只命中"相对"那种解释**。现在 `pck_strip.py` 读入和写出前各做一次
md5 全量自检，不通过就拒绝写出。

#### 验收热更包：哪条路能走、哪条不能

⛔ **`--main-pack <pck> --script <探测.gd>` 不行**（2026-10-30 实测，文档早先写的这条是错的）。
热更包按设计**不含 assets**，而脚本里有 `preload("res://assets/vfx/xxx.png")`，
单独拿它当主包 ⇒ `Parse Error: Preload file "..." does not exist` ⇒
`Failed to compile depended scripts` ⇒ 探针连第一行都跑不到。
换句话说：这条路验证的是"pck 能否自给自足"，而不是"代码是不是新的"。

⛔ **发布版 EXE 不认外部 `--script`**：`[updater]` 的日志会打出来，
但指定脚本一行都不执行（测试脚本的 `print` 全空）。

✅ **能用的两条**：

**① 比 gdc 的 size+md5（最硬，推荐）** —— 与上一版包逐条对比，
「变了的脚本集合」必须**正好等于**本次改动的源文件集合，多一个少一个都说明打错了包：

```bash
# 用 tools/pck_ls.py 的解析逻辑，取两个包的 scripts/*.gdc 的 (size, md5) 做差集
# 例：b21→b22 恰好 4 个变化，与改的 4 个源文件一一对应
#   eve_battle_scene.gdc       59084 -> 59867 (+783)
#   eve_deploy_controller.gdc   6495 ->  6888 (+393)
#   eve_fleet_factory.gdc       3175 ->  3257  (+82)
#   eve_ship_dossier.gdc       16265 -> 16255  (-10)
```

> 手法细节：`.gdc` 是 **zstd 压缩**的（`GDSC` 头之后紧跟魔数 `28 b5 2f fd`），
> 但要验证"改没改"不需要解压 —— 直接比目录项的 md5 就够了。
> 解压后也搜不到标识符（tokenizer 把名字编码成紧凑形式），别在这上面绕。

**② 客户端本体跑热更（验的是"玩家会不会崩"）**：
`build/` 里那版 EXE 启动 → 下包 → 重启后应打印
`[updater] 已挂载热更包 user://update.pck`，且 `update_state.cfg` 里 `boot_fail = 0`。
包内 `build_info.json` 用 pck 解析读出来应是新版本号。

### 客户端实现要点（`scripts/core/eve_updater.gd`）

| 机制 | 为什么 |
|---|---|
| **autoload 排第一位** | `load_resource_pack` 必须在其他脚本实例化前调用，越晚挂载越多东西换不掉 |
| **失败静默** | 服务器挂了 / 清单 404 / 校验不过 ⇒ 一律照常用本地版本进游戏，⛔ 绝不拦启动 |
| **SHA256 校验** | 下到半个包挂上去 = 启动即崩 |
| **坏包三次自动回退** | 挂载后连续 3 次没走到主菜单 ⇒ 删包退版本。**这是玩家自己救不回来的唯一场景**（包坏了连设置页都进不去），必须自动 |
| **版本号读 `res://build_info.json`** | 它跟着 pck 一起被打包，挂载后自动变成新版本号 ⇒ 右下角显示不会"更新完还是旧号" |

### ★ 2026-11-07 改造（二版）：检查 → 询问 → 进度条 → 重启

改造前 `check()` 拉到清单就**直接下**，玩家全程无感 —— 好处是更新率 100%，
坏处是**玩家不知道自己被更新了**：正在打一局，下次重启界面/数值全变，像游戏被人改过。

#### 第一版为什么不作数

第一版把「检测 / 下载 / 进度」写进了 `EveUpdater`（一个 autoload），主菜单靠
`_up_has()` 查它的新成员再连信号。但 autoload 节点在 pck 挂载**之前**就实例化，
用的永远是基础包里的老脚本 ⇒ 老客户端上 `update_available` / `download_finished` /
`pending_update` **一个都不存在** ⇒ `_wire_updater()` 直接 `return`。

结果：**弹窗代码写完了、发了版，却在任何真实玩家机器上一次都没跑过。**
（同期 b39 还是个坏包，直接黑屏，更没人看得到。）

#### 现在的结构

```
主菜单 _ready() 之后 1.5s
  └─ UpdateCheck（普通 Node，主菜单 new 出来的）
       · 自己读 res://build_info.json
       · 自己拉 version.json、比 code
       · 自己下载（多源）+ sha256 校验 + 自己装包
       ⛔ 一个 EveUpdater.xxx 都不碰
            │
            ├ asked            → 面板「当前 V35 → 最新 V41 · 1.12 MB」[稍后][现在更新]
            ├ progressed       → 面板切进度条：43% / 1.1 MB / 1.12 MB
            ├ ready_to_restart → 面板「已就绪 · 重启生效」[稍后重启][立即重启]
            └ failed           → 面板「更新失败」[关闭][重试]
```

**为什么这样就一定能到达玩家**：主菜单脚本会被 pck 覆盖，所以这套逻辑以后可以靠热更改。
这是与第一版的唯一本质区别。

#### 与老 `EveUpdater` 的共存（关键设计）

基础包（≤ b35）里的 `EveUpdater._ready()` 在启动 2 帧后**无条件静默下载**，
这段代码在 autoload 里、热更改不掉。所以新检查器一启动就可能发现
`user://update.pck.part` 正在被别人写。

⇒ 两个数据源都认：

| 场景 | 处理 |
|---|---|
| 老 EveUpdater 已经在下载 | **观察** `.part` 的字节数增长，面板显示同一个进度条（`allow_dismiss = true`，允许「后台继续」） |
| 没人下载 | 自己下到 `user://update_ui.part`（独立文件名，⛔ 绝不和它抢同名文件） |
| 本地 `update.pck` 已等于清单 size + sha256 | 直接「已就绪」，⛔ 不再问一遍「要不要下载」 |

也就是说：**哪怕这波下载不是玩家点的，他至少看得见进度、看得见「重启生效」。**

#### 实现要点

| 要点 | 为什么 |
|---|---|
| 检查器是普通 Node，不是 autoload | autoload 注册表跨不过 pck 边界（b39 事故的根因） |
| 面板 `extends Control`，不是 `Window` | `Window` 是真 OS 窗口，系统标题栏/字体度量换不掉皮 |
| 延迟 1.5s 用**子 Timer**，不用 `await create_timer()` | 玩家可能在这 1.5s 里点「开始游戏」⇒ 节点被 free，`await` 恢复时报 "object was freed" |
| 进度靠 `_process` 轮询（`get_downloaded_bytes()` 或 `.part` 大小） | `download_file` 模式**没有进度回调**；按整数百分比节流，否则进度条会抖 |
| 下载中**点卡片外不关闭** | 手滑点空白就关掉进度条，玩家会以为「更新被取消了」 |
| sha256 校验不过就换源 | 加速站可能缓存旧包 / 被劫持 |
| `restart_app()` 分三平台 | web 无进程重启；Android 自拉起要 Intent（没集成）；**编辑器里调 `create_instance` 会把编辑器再开一份** |
| 「稍后」不持久化 | 用户拍板：下次启动再问。⛔ 别加 `skipped_code` 记忆 |

⚠️ **`code` 仍然是唯一比较依据，而且必须真的涨**，否则客户端收不到。

⚠️ 时序推论：检查器本体在 pck 里，**b40 及以前的客户端没有它**。
所以它们是静默拉到 b41，**从 b41 起才具备「先问再下」的能力**
—— 老客户端第一次看到弹窗，是从 b41 往 b42 升的那一次。

**怎么验（不用等真发版）：**

| 验什么 | 怎么造 |
|---|---|
| 弹窗 + 版本号 | 把 `build_info.json` 的 `code` 临时改成比服务器小的值，并把 `user://update.pck` 先移走，跑游戏 |
| 进度条 | 点「现在更新」⇒ 面板出现进度条 + `43%` + `1.1 MB / 1.12 MB` |
| 「稍后」不记住 | 点稍后 → 退出 → 再进 ⇒ 应该**再弹一次** |
| 下载中点外面 | 进度中狂点卡片外 ⇒ 面板**不该关** |
| 立即重启 | 就绪后点「立即重启」⇒ PC 上自动拉起新进程 |
| 断网 | 拔网线后点「现在更新」⇒ 面板显示「更新失败」+ 可重试 |
| 逻辑回归 | `godot --headless --script tools/verify_update_ui.gd`（35 条，离线） |
| 上报回归 | `godot --headless --script tools/verify_report.gd`（19 条，离线） |

## 六、安全加固（2026-10-30）

起因：0.14.10 发到玩家群后，担心「有人拿到端口就 DDoS」。实测当天**并没有被攻击**
（3 秒采样入站 2.4 KB/s、出站 2.8 KB/s，`ss -s` estab 4 条，
`Failed password` 计数 0）。但顺手查出两个**真实**问题，都已修。

### 6.1 要认清的软肋在哪

这台机器真正的问题是**出网只有 4 Mbps**，不是抗 DDoS 能力。

- 单个玩家下 6 MB 热更包 = 12 秒，刚好跑满带宽，一点余量都没有
- **20~30 个连接同时拉包就能把服务弄瘫** —— 这不需要攻击，
  发版瞬间群里几十个人一起点更新就够了
- 真正的 DDoS（几百 Mbps 起）反而轮不到我们操心：腾讯云轻量自带基础防护，
  超过阈值会直接黑洞掉 IP，既不可控也不用配

### 6.2 已做的三层

| 层 | 措施 | 文件 |
|---|---|---|
| 云防火墙 | 只开 22 / 80 / 27100-UDP | 控制台 |
| 系统 iptables | 80：单 IP 并发 24、新建 40/s<br>27100：单 IP UDP 300/s<br>22：单 IP 并发 6、新建 6/min | `tools/relay/harden_node.sh` |
| 应用 Caddy | 关目录浏览、只许 GET/HEAD、抹 `Server` 头、访问日志 | `tools/relay/Caddyfile.dist` |

开机自启由 `eve-firewall.service` 保证（`harden_node.sh` 会装）。
**没有它，重启一次规则全丢，而且从表面完全看不出来。**

⚠️ 所有限流都按**源 IP** 分桶。运营商 CGNAT 下多个玩家可能共用出口 IP，
**这三个值不能往小调**。

### 6.3 SSH 加固：五档手段，按「会不会把自己锁死」排序

现状（2026-10-30 实测 `sshd -T`）：`port 22`、`PermitRootLogin yes`、
`PasswordAuthentication yes`、`MaxAuthTries 6`。公网 22 挂着，自动爆破是全天候的。

关密码**不是唯一手段**，而且它是**最危险的一档**（配错就永久进不去）。
按性价比排：

| 档 | 手段 | 效果 | 自锁风险 | 谁来做 |
|---|---|---|---|---|
| ① | **云防火墙把 22 限成只放行你自己的 IP** | ★★★★★ 攻击面直接归零 | 中（家宽 IP 一变就连不上，可用 WebShell 救） | 控制台点两下 |
| ② | **fail2ban**（失败 5 次封 1 小时） | ★★★★ 挡掉 99% 脚本爆破 | 无（只封失败的 IP） | ✅ **已装好** |
| ③ | 改 SSH 端口（22 → 高位端口） | ★★ 只减少日志噪音，不减攻击面 | 中 | 手工 |
| ④ | 禁 root 直登 + 建普通用户 sudo | ★★★★ | 低 | 手工，且要先建好用户 |
| ⑤ | 关闭密码，只认密钥 | ★★★★★ | **最高** | 手工，必须先用 VNC 验好 |

**② 已经做了**（2026-10-30）：

```ini
# /etc/fail2ban/jail.local
[DEFAULT]
bantime  = 1h
findtime = 10m
maxretry = 5
backend  = systemd      # ⚠️ 这台机器没有 /var/log/auth.log，不加这行 jail 匹配不到任何东西
ignoreip = 127.0.0.1/8

[sshd]
enabled = true
port    = 22
```

`systemctl status fail2ban` / `fail2ban-client status sshd` 看战果。
误封自己就 `fail2ban-client set sshd unbanip <你的IP>`。

⚠️ **为什么 ② 能被自动化通道做、⑤ 不能**：运维接口对 `/etc/ssh`、`sshd`、
`PasswordAuthentication` 这些**关键词**一律 `AccessDeny`（连把脚本写到
`/usr/local/sbin` 都不行，因为脚本体里含这些词）。这是平台故意防"把用户锁在
自己机器外面"，不该绕过。fail2ban 不碰这些词，所以能做。

**① 是性价比第二高的**，而且完全可逆：控制台 → 防火墙 → 把 22 的规则来源改成
`你的IP/32`；需要时删掉规则就恢复全世界可连。**如果你家宽带是动态 IP，别做这条**，
否则每次换 IP 都要开控制台改。

**⑤ 只在你能用 VNC 进去之后再做**（控制台 → 实例 → 登录 → VNC）：

```sh
cat > /etc/ssh/sshd_config.d/00-eve-harden.conf <<'EOF'
PermitRootLogin prohibit-password
PasswordAuthentication no
KbdInteractiveAuthentication no
EOF
sshd -t && systemctl reload ssh || rm -f /etc/ssh/sshd_config.d/00-eve-harden.conf
```

回滚（还能进 WebShell 的话）：`rm -f /etc/ssh/sshd_config.d/00-eve-harden.conf
&& systemctl reload ssh`

**最彻底的一档（⑥，表里没列）**：直接把 22 从云防火墙删掉，平时只用控制台的
WebShell / 自动化助手操作。攻击面真的归零，代价是每次运维都得开控制台，且
WebShell 出问题只能走 VNC。

⚠️ 顺带提醒：既然要在防火墙限 IP，**别忘 27100/UDP 是对玩家开放的**，那不能限。

### 6.4 热更包的多源分发

为了避免「发版瞬间把带宽吃干」，清单 `version.json` 里 `pck` 支持多个地址：

```json
"pck": {
  "urls": ["加速站…", "自建节点…"],
  "url":  "自建节点…",
  "size": 6012948,
  "sha256": "…"
}
```

- `urls` 给**新客户端**：按顺序试，失败/超时自动换下一个
- `url` 给**0.14.10 那批老客户端**：它们没有多源能力，必须指向最可靠的源（自建）
  ⇒ 所以 `url` 不要写加速站，加速站一挂老客户端就静默收不到更新

⚠️ **2026-10-30 实测（作者网络）**：

| 源 | 结果 |
|---|---|
| `ghfast.top` / `gh-proxy.com` / `gh.llkk.cc` | **全部超时** |
| `ghproxy.net` | 200，7.4 秒（慢） |
| `github.com` 直连 | 200，1.7 秒 |
| 自建节点 | 200，506 KB/s（最稳） |

⇒ 加速站**不是**普遍可用，只能当"能用就更快"的备选，**自建必须留作保底**。

⚠️ 顺带修掉一个躺了两天的 bug：下载包沿用了拉清单的 6 秒超时，
而 6 MB 在 506 KB/s 下要 12 秒 ⇒ **永远下不完就被自己砍断**。
现在拆成 `DL_TIMEOUT_TRY = 15s`（备选源，连不上就快点换）和
`DL_TIMEOUT_LAST = 300s`（最后一个源，慢速网络也给足时间）。

### 6.5 「排队中」提示可不可行（2026-10-30 评估，**尚未实现**）

结论：**能做，但对现在这个瓶颈没用**。理由在"限流发生在哪一层"。

现在的限流全是 iptables 做的（`connlimit` / `hashlimit`）。**内核丢包没有嘴**：
包被丢掉，玩家那边只会看到"连接超时 / 一直进不去"，我们没有任何机会
塞一句"前面还有 3 桌，请稍候"进去。想让玩家看到提示，限流必须从内核搬到应用层。

要做的话，改动面：

1. `tools/relay/eve_relay_server.js`
   - 维护活跃房间数 `rooms.size()`，设软上限 `MAX_ROOMS`
   - 超过上限时，对**新房间码**的首个包不再转发，改回一个控制包
2. 协议扩展（现在 `[EV][8字房间][1字节身份][ENet负载]`）
   - 身份字节目前只有 `0=房主 / 1=加入方`，还剩 254 个值可用
   - 约定 `0xFE = BUSY`，负载里带 2 字节"前面还有几桌"
   - ⚠️ 老客户端**不认识 0xFE**，会把整个包当 ENet 数据报丢给本地 ENet
     （ENet 会丢弃非法包，不会崩，但也不会显示排队）⇒ 排队提示只有
     **更新过的新客户端**才有，老客户端仍是"连不上"
3. `scripts/net/eve_udp_relay.gd`：解出 `0xFE` ⇒ 置 `queue_rank` 并继续每 1.5s 重试
4. 联机大厅 / 等待界面：读 `queue_rank` 显示「服务器繁忙 · 前面还有 N 桌 · 正在排队」

**为什么建议先不做**：

- 真实瓶颈是 **4 Mbps 出网带宽**，不是连接数或 CPU。带宽满了的表现是
  **卡、丢包、延迟飙升**，不是"连不上"——排队提示解决不了"卡"。
- 2 核 2G 撑几十桌 UDP 转发毫无压力（转发就是 11 字节头 + 原样转发，没有状态机）。
- 带宽里最大的一块本来也不是对战流量，而是**热更包并发**——已经通过
  ① 剥 icudt 把包从 6MB 削到 1.02MB、② 清单多源分流到 GitHub 加速站，
  把它从"发版瞬间占满 4 分钟"压到"40 秒以内"。

⇒ **先观察**。真出现"进不去 / 连不上"的反馈，再按上面四步做。
如果哪天要做，注意 `MAX_ROOMS` 只能按**带宽**估，不能按 CPU 估。
