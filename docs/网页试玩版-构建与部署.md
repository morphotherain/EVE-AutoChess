## 二、怎么打这个包

```bash
bash tools/build_web.sh            # 或 tools/build_web.sh <godot路径>
```

脚本干三件必须做的事（少一件就出问题）：

1. **主场景临时改成 `scenes/doudizhu.tscn`** —— Web 导出没有"每个预设一套主场景"这回事，
   只能改 `project.godot`，导完 `trap` 还原。
2. **临时删掉 `MCPRuntimeProbe` autoload** —— 它的脚本不在导出白名单里，
   留在包里启动即报 `Failed to load autoload`。
3. **`gzip -9 index.wasm`** —— Caddy 侧开了 `precompressed gzip`。

产物在 `build/web/`，八件：`index.html/.js/.pck/.wasm/.wasm.gz` + 三个图标/worker。

## 三、导出预设为什么长这样

`export_presets.cfg` 的 `[preset.3]`（名 `Web`）：

```ini
export_filter="scenes"
export_files=PackedStringArray("res://scenes/doudizhu.tscn")
include_filter="scripts/*, i18n/*, assets/fonts/*, assets/cards/*.png,
                assets/audio/sfx/*.ogg, assets/audio/ambience/*.ogg,

                assets/backgrounds/caldari-c02-nebula-4096.png,
                assets/backgrounds/stars_layer_1920x1080.png"
```

⛔ **只写 `scenes` 模式会漏东西**，实测漏了三类：

| 漏的 | 症状 | 补法 |
|---|---|---|
| autoload 的脚本依赖 | `Parse Error: Preload file "res://scripts/core/eve_text.gd" does not exist` → 整页黑屏 | `scripts/*` 全带上 |

`export_filter="all_resources"` 也能跑通，但会把 161 MB 的 `assets/ships3d` 一起拉进来，
不划算。

## 四、自走棋试玩版：85 MB 的账（2026-11-04 推翻旧结论）

**旧结论是「上不了」，那是错的。** 当时只算了源文件体积（`ships3d` 161 MB），
既没算 VRAM 压缩后的实际值，也没意识到**贴图过采样了 8~16 倍**。

### 真实数字

| 阶段 | pck | 首屏 | 说明 |
|---|---|---|---|
| 全量 `all_resources` | 253 MB | — | 第一次量出来的基线 |
| 贴图 `size_limit` 压到 512 | 101 MB | 110 MB | 只改了 156 个 `.import` 的一行 |
| 再排掉卡牌 / 多余 BGM | 93 MB | 102 MB | |
| **pck 开 Caddy 预压缩** | 72 MB | **85 MB** | `index.pck.gz`，Caddy `precompressed gzip` 自动吐 |

首屏 = `index.pck.gz` 75 MB + `index.wasm.gz` 9.7 MB ≈ **85 MB**。
4 Mbps 约 2.8 分钟；浏览器第二次访问走 `Cache-Control: max-age=3600`，秒开。

⚠️ pck 里主要是已压缩过的 `.ctex` 纹理，gzip 只压得出 21%（93→72 MB），
但一次 `gzip -6` 只要 3.6 秒 CPU，白给的 21 MB 不压白不压。

### 省下来的 140 MB 在哪

| 贴图 | 原尺寸 → 包里 | 压缩后 → 包里 | 省 |
|---|---|---|---|
| 法线 `_n` ×52 | 2048×1024 · 81 MB | 512×256 · 5.2 MB | 76 MB |
| 高光 `_s` ×52 | 2048×1024 · 39 MB | 512×256 · 4.3 MB | 35 MB |
| 漫反射 `_d` ×52 | 2048×1024 · 39 MB | 512×256 · 17.7 MB | 21 MB |

**为什么敢压**：棋盘上的船在屏幕上只有一两百像素，2048 宽等于每像素 8~16 个 texel，
压到 512 依然是 2~4 倍过采样。
A/B 实测（同机位、同帧、船体区域）：

```
像素差：均值 2.43/255 · p95 = 18 · 最大 106
4 倍最近邻放大后目视：金色饰条、板缝、涂装分色全部保留
```

⚠️ **唯一要认的代价**：玩家把镜头推到最近看船时，纹理比原来软一点。

### 怎么做到「只压网页、不动桌面」

贴图尺寸在 `.import` 里，是**全平台共用**的。所以不能直接改工程文件 ——
`tools/pipeline/web_tex_downscale.py` 负责在构建期改、导完再改回，
构建脚本（`tools/build_web_pve.sh`）负责串起来：

```
改 .import → godot --import（重建缓存）→ 导出 → 改回 .import → godot --import（还原缓存）
```

⚠️ 最后那步「还原缓存」不能省。省了的话 `.godot/imported` 里留着网页档的小图，
**下次桌面版导出会直接拿它打包，桌面画质就悄悄降级了**。

### 还能再压什么（按性价比）

| 项 | 现在 | 可做到 | 代价 |
|---|---|---|---|
| 舰船模型 scn | 24.8 MB | ~15 MB | 需要 gltfpack/Draco 预处理 glb，重跑管线 |
| `assets/vfx` | 10.9 MB | ~5 MB | 序列帧图集降分辨率，爆炸会糊 |
| `icudt_godot.dat` | 4.6 MB | 0 | 删了怕影响中文取词，没敢动 |
| 分章加载 | — | 首屏 25 MB | `load_resource_pack()` 按需拉，工程量最大 |

### 引擎侧为 web 做的三件事

全部判 `OS.has_feature("web")`，桌面/安卓一行都不受影响：

1. **跳过开场剧情**（`eve_main_menu.target_scene_for_start`）
   13 MB 视频 + 逐句演出，首屏等不起，玩家点「试玩」的期待本来就是直接开打
2. **开局送 3 艘船并上阵**（`eve_battle_scene._seed_web_starter_fleet`）
   ⚠️ 这条不是「贴心」，是**必须**：`eve_phase_battle.start()` 开头就有
   `if own.is_empty(): return null` —— 空手点「开战」连敌方视觉都不会生成，
   玩家看到的是一片空星空，以为网页版坏了
3. **联机走 WebSocket 中继**（`ddz_room._use_ws`），浏览器没有 UDP/ENet

## 五、踩过的坑（都很贵）

### 1. 中文全是乱码 / 方框（2026-11-04 修正过两次结论）

浏览器里没有"系统已装字体"这回事，`SystemFont` 退化成引擎自带默认字体（无中文字形）。
解法：随包分发 **Noto Sans SC 子集**（OFL 授权，`assets/fonts/` 两个文件各 616 KB）。

⛔ 挂载**不能放 `_init()`**：那时节点还没进树，直接报
`Parameter "data.tree" is null`，白干一轮（实测导了三次才发现）。

子集化脚本：`tools/pipeline/subset_font.py`，扫 `scripts/ scenes/ i18n/ data/ assets/ui/`
里出现的所有字符（含 csv 里的舰船名），2108 个字 → 616 KB。

#### ⚠️⚠️ 只挂 `Theme.default_font` 远远不够（本条真正的坑）

第一版只做了这两件事，以为就完事了：

```gdscript
ThemeDB.fallback_font = f
var t := Theme.new()
t.default_font = f
get_tree().root.theme = t
```

结果：**主菜单中文完全正常，进战斗场景满屏方框**。
方框是 Noto 的 `notdef`（方框内部有交叉网格线），第一眼极容易误判成
"分辨率太低糊了" 或者 "字体子集缺字"。

真因是 Godot 的主题查找顺序：

```
控件 override → 父链上的 theme → 【内置默认主题】 → ThemeDB.fallback_font
```

`Theme.default_font` **只在「该类型整条链都没定义 font」时才顶上**。
而内置默认主题里 `Label/fonts/font` = **Open Sans SemiBold**（无中文）
⇒ 永远先命中它，中文只能是 notdef。

证据是逐个 Label 打印 `get_theme_font("font")` 拿到的：

| 控件 | 解析到的字体 |
|---|---|
| 自己 `Label.new()` 新建的 | `Noto Sans SC` ← 走了 root.theme.default_font |
| HUD 里真实存在的 Label | `Open Sans SemiBold` ← 内置默认主题抢先 |

两者在同一棵树下，差别只在"内置主题里有没有这个类型的 font 项"。

✅ 正确做法：**逐个类型**把内置默认主题的 font 项换掉。

```gdscript
var dt := ThemeDB.get_default_theme()
dt.default_font = f
for ty in dt.get_type_list():
    if dt.has_font("font", ty):
        dt.set_font("font", ty, f)
```

这是唯一能一次覆盖 Label / Button / RichTextLabel / … 全部控件、
又不用改 88 处 `add_theme_font_size_override` 调用点的办法。

⚠️ **别拿"主菜单正常"当字体没问题的证据** —— 主菜单那批控件恰好没被内置主题命中，
这次就是被它骗过去的。验收必须**进战斗场景看 HUD 与商店**。

### 2. 导出模板根本没有 web（已解决）

> **2026-11-04 更新**：`%APPDATA%\Godot\export_templates\4.7.2.stable\` 现在已有
> 全部 web 变体（`web_release` / `web_nothreads_release` / `web_dlink_release` /
> `web_dlink_nothreads_release`，另加 debug 版），`zipfile.testzip()` 全部 OK。
>
> **判断模板对不对的最快办法**：导出产物的 `index.wasm` 字节数应该等于
> 模板里 `godot.wasm` 的字节数（实测 `39514754`）。不等 ⇒ 版本或变体不匹配，
> 别急着调代码。

下面这段是当初模板缺失时的应急方案，留着备用：

整包 `Godot_v4.7.2-stable_export_templates.tpz` 是 **1.2 GB**，
镜像 0.15~0.6 MB/s，还要先卡在 30 MB。

解法：`tools/pipeline/fetch_web_tpl.py` —— ZIP 的中央目录在文件尾，
用 HTTP Range 把 `web_*.zip`（`web` 与 `web_nothreads` 两套，共 6 个）单独抠出来，
只下 **~46 MB**。

⚠️ Godot 4.7 的非线程模板叫 `web_nothreads_*.zip`，`variant/thread_support=false` 时
只认这一套，两套都要。

### 3. 热更器在网页版刷跨域错误

`EveUpdater` 拉 `http://49.233.138.141/update/version.json`，跨域必被 CORS 拦。
网页版的包就是站点直接分发的，没有"本地热更"这回事 ⇒ `_ready()` 里
`if OS.has_feature("web"): set_process(false); return`。

### 4. 无头浏览器验证输入，别硬刚

`Page.captureScreenshot` 在画面无变化时返回同一帧（md5 一样），
`Input.dispatchMouseEvent` / `Input.dispatchTouchEvent` 注入到 Godot canvas 也不一定生效。
**结论：点击类交互只能让真人在真浏览器里点**，自动化只验证到"场景能加载 + 文字正常"。

### 5. 服务器拉 raw.githubusercontent 会间歇超时

2026-11-04 实测两次 40s timeout。一律改走
`https://gh-proxy.com/https://raw.githubusercontent.com/<owner>/<repo>/<sha>/<path>`。

### 6. 网页版**全程静音**，而且一条报错都没有（2026-11-04）

症状：斗地主进桌没有 BGM，控制台只有一行
`WARNING: [EveAudio] 音源缺失（静默跳过）：ddz`。

排查过程里我先搞错了一次，值得记下来当反面教材：

- 我拿 `tools/pck_ls.py` 看包内容，只 grep 到 1 个 `.oggvorbisstr`，于是判断
  「音频一个都没进包」，还照着这个错误结论加了一套 `preload` 清单机制（白干两轮）。
- **真相**：`pck_ls.py` 只打印汇总 + 最大的 20 个条目，grep 当然只看到一条。
  sfx / ambience 一直在包里，**只有 `assets/audio/music/ddz_01.ogg` 没进**，
  因为 Web 预设的 `include_filter` 里根本没写 music 目录。

修法一行：

```
include_filter="..., assets/audio/music/ddz_01.ogg, ..."
```

BGM 2.83 MB 进包，pck 20 MB → 23 MB，`[EveAudio] 音源缺失` 告警消失。

**教训**：`pck_ls.py` 不是「列出全部」，判「有没有进包」要自己按扩展名统计。
顺手加了 `tools/web_audio_probe.py`：从浏览器里回读 AudioContext 状态与
`currentTime` 是否在走，这才是「有没有声音」的硬证据（实测 `running`，
两次采样差 2.01 秒 ≈ 真实流逝）。

⚠️ 探针**不要**加 `--autoplay-policy=no-user-gesture-required`：
那会绕过浏览器的自动播放限制，测出来的「有声音」在真浏览器里不成立。

### 7. 浏览器没有 UDP ⇒ ENet 联机在网页上整条不存在（2026-11-04）

网页版「联机对战」按钮点不动，根因不是按钮坏了：

| 桌面 / 安卓 | 浏览器 |
|---|---|
| ENet（UDP）+ EasyTier TUN 隧道 | 没有 UDP socket，也没有 TUN |
| `eve_ddz_transport.gd` | 只能 WebSocket |

解法是**同一套接口的第二份实现**，`ddz_room.gd` 一行网络逻辑都没改：

- `scripts/net/eve_ws_transport.gd`：`host_start/join/send_to/broadcast/poll/stop`
  与 ENet 版完全对齐，信号也一样（`peer_joined/peer_left/connected_ok/connect_failed/packet`）。
- `tools/relay/ws_relay_server.js`：零依赖手写 WebSocket（只监听 `127.0.0.1:27101`），
  按 8 位房间码分组转发；**房主的「服务端身份」由它扮演**（固定 id=1）。
- `deploy/Caddyfile`：`reverse_proxy @relay 127.0.0.1:27101`，对外只有 443 一个入口。
- 客户端在 web 下 `skip_tunnel = true`（浏览器没有 TUN），并强制走 WS 传输层。

拓扑差别只有一处，想清楚就通了：

```
ENet ：房主真的在监听端口，加入者连房主
WS   ：所有人（含房主）都是中继的客户端，中继按房间码分组
       房主视角完全一致（peer_id=1 是自己，收到 2/3/4 的包）
```

验证：`tools/relay/ws_relay_test.js`（8 条断言，支持 `ws` 和 `wss`）
+ `tools/probe_ws_transport.gd`（用游戏自己的传输层跑建房→加入→双向收发）。

### 8. `--export-pack` 用的是**旧的脚本编译缓存**（2026-11-04，最坑的一条）

现象：改了 GDScript，`--export-pack` 重新导出、重新加载，
**运行时的 print 还是旧代码**。同一份代码用 `--export-release` 就正常。

排查过程（走错了两步，记下来免得重走）：
1. 先怀疑浏览器缓存 ⇒ 每次 CDP 都是新 profile，排除。
2. 再怀疑 `grep pck 找不到新字符串` ⇒ `.gdc` 是二进制 token 格式，
   `grep -a` 本来就不该指望，这个判据是错的。
3. 最后把 pck 里的 `eve_battle_scene.gdc` 抠出来看：60888 字节，
   里面**根本没有新加的字符串** ⇒ 结论明确。

**规则：只要改了脚本，就用 `--export-release`（走完整导入/编译），
不要用 `--export-pack`。** 后者适合「只换资源、脚本没动」的场合。

### 9. 无头浏览器点 canvas：坐标换算错了几十像素（2026-11-04）

`--window-size=1280,800` 的窗口，canvas 实际只有 **1094×581**
（浏览器内容区 ≠ 窗口尺寸）。当时兜底脚本按 `cx * canvas.width / W` 换算，
把每个点击都缩到 0.855 倍 ⇒ 点「开始简单」按钮落到了卡片空白处，
表现就是「点了没反应」。

**规则：截图坐标 = CSS 像素 = canvas 坐标，直接加 `rect.left/top` 用，别做窗口换算。**
判据用「点完画面有没有变」，别用「有没有报错」—— 点偏了不报任何错。
已对 `wss://xshy.top/relay` 全绿，说明「浏览器 → Caddy → 中继」整条链路通。

⚠️ 两个必须记住的坑：

- **中继必须单独接 socket `'end'`**。只挂 `'close'` 时，对方**直接断网/关进程**
  （不是发 close 帧）这种情况可能永远收不到通知 ⇒ 房间不回收、房主一直等一个死连接。
- **Caddy 的 `idle` 会掐掉空闲 WebSocket**。原来设 45 秒，房主建完房在大厅等人就会被断；
  现在中继每 30 秒发一帧 ping（opcode 9，浏览器和 Godot 都自动回 pong），
  同时把 `idle` 放宽到 120 秒兜底。

### 10. 无头浏览器的 rAF 被节流 ⇒ 会误判「网页版打不起来」（2026-11-05）

用无头 Chromium 打开线上的 `/pve/` 连拍，看到的画面是：3 艘船飘在太空里、敌方一艘都没有、
92 秒里坐标一动不动、界面还停在准备阶段的商店。第一反应必然是「战斗没启动 / 敌方舰队没生成」。

**全是假象。** 证据在时钟上：59 秒真实时间里，游戏内时钟只从 `00:07` 走到 `00:04`
—— 虚拟时间跑到了真实时间的 **1/20**。无头 Chrome 把页面当成「不可见」，
`requestAnimationFrame` 被节流到 ~1 fps，Godot 的 `delta` 跟着变得又大又稀，
准备阶段的 30 秒倒计时在现实里要走上好几分钟，自然什么都看不到。

改法（`tools/web_play_probe.py`，`HEADED=1` 走有头）：

```
--disable-backgrounding-occluded-windows
--disable-renderer-backgrounding
--disable-background-timer-throttling
--disable-features=CalculateNativeWinOcclusion
+ CDP Page.bringToFront     # 有头也会被别的窗口盖住而降帧
```

改完立刻正常：36 秒时准备倒计时到 `00:02`（≈真实 30 秒），65 秒时敌方首领带血条出现在
中央、有开火闪光与跳伤害数字、右侧战斗日志在滚。

**规则：无头模式只能验「能不能启动 / 中文对不对 / 有没有报错」，
凡是和「时间推进」有关的（倒计时、战斗节奏、开火、结算）必须 `HEADED=1`。**
判断依据要看**时钟走的快慢**，不要看「船动不动」—— 船不动可能只是 30 秒还没到。

## 六、部署步骤（服务器侧）

```bash
# 1. 拿包（走 GitHub Release + 镜像，别指望 ssh/scp，2026-11-04 起 22 端口握手被掐）
curl -fsSL 'https://gh-proxy.com/https://github.com/xshynews/EVE-AutoChess/releases/download/web-ddz-v1/web_ddz.zip' -o /tmp/play.zip

# 2. 解压（38 MB，别放前台，会超网关 30s）
mkdir -p /var/www/eve/play && cd /var/www/eve/play && nohup unzip -oq /tmp/play.zip > /tmp/unzip.log 2>&1 &
chown -R www-data:www-data /var/www/eve/play
```
