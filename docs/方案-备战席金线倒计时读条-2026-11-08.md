# 备战席金线条 → 准备倒计时读条（2026-11-08）

> 状态：**用户 2026-11-08 定案 C 画法（余段留中间），已实装并随 b43 发版**。
> 三种「向中间靠拢」的画法对照见第四节。

---

## 一、这条线本来是什么

`EveBenchRail._draw_layer_line()` 画的 1.5px 金线，位置在备战席控件顶部
（设计坐标 y = 756 / 控件 y = 0.5），横跨整个 1200px 宽。

它的原始语义写在 `eve_bench.gd` 头注释里：**「格带是浮在棋盘外侧的一层平台」
的唯一视觉声明** —— 金线 = 平台的近端边缘高光。用户 2026-09-22 明确要「高差明显」。

⇒ 所以这次改动的**硬约束**：它变成读条之后，**不能把「平台边缘」这个身份丢掉**。
否则不读秒的时候（战斗 / 结算 / 新手模式无限时）那条线会消失，格带看起来像
「飘在半空的一排格子」。

---

## 二、时间从哪来（不造第二份真相源）

顶条 `EveCommandBar` 已经持有 `time_left` / `time_total`，`tick(delta)` 每帧递减，
`set_stage(total)` 时置满。它是倒计时的**唯一真相源**（`stage_seconds_left()`
也是只读它）。

推给金线的链路（**单向投影，全程不存时间**）：

```
battle_scene._process  (PREP 分支)
  └─ hud.tick_stage(delta)
       ├─ command_bar.tick(delta)          ← 唯一递减的地方
       └─ hud._push_stage_clock()
            └─ bench_rail.set_stage_time(command_bar.time_left, command_bar.time_total)
                 └─ _StageLine.ratio / hot → queue_redraw()
```

⛔ **金线自己不存剩余时间**，也不递减。再存一份 ⇒ 两处必然漂移，而且暂停时
还会各走各的（项目里「别造第二份真相源」是同一条规则）。

### 什么时候读、什么时候不读

| 阶段 | 是否读秒 | 金线长相 |
|---|---|---|
| 准备（`_phase == 0`，`total > 0`） | 读 | 两段 + 全宽暗轨 |
| 战斗 `_phase == 1` | **不读** | 原样完整金线 |
| 结算 `_phase == 2` | **不读** | 原样完整金线 |
| 新手模式准备（`total == 0` = 不限时） | **不读** | 原样完整金线 |

⚠️ 战斗阶段顶条走的是**战斗时限**，那跟「备战席还能操作多久」完全无关。
让金线跟着战斗时限收缩，玩家会以为备战席快要没了。
`_phase` 存在 HUD 上（`set_phase` 已经在所有阶段切换点被调用），
`set_phase` / `set_stage` 里都立刻 `_push_stage_clock()` 一次，不等下一帧 tick ——
否则开镜那一帧会看到上一回合的残留长度。

## 三、为什么读条画在独立子节点上

`sizing`：金线每帧都在变。如果继续写在 `EveBenchRail._draw()` 里，
每帧 `queue_redraw()` 会把**8 张 512² 立绘缩图 + 8 个吨位图标 + 40 条格线**
整套 canvas item 一起重建 —— 只为让一条线挪 2 像素。

⇒ 拆出 `class _StageLine extends Control`（内嵌类，同 `eve_command_bar._RingGauge`
的既有做法），高 4px、贴控件顶部、`MOUSE_FILTER_IGNORE`。它只有 3 段
`draw_line`，重绘几乎免费。

⚠️ 尺寸同步用 `resized` 信号手动摆 `position`/`size`，**不用 anchors preset**：
本控件的 `size` 是 HUD 布局时直接赋值（`bench_rail.size = b.size`），
锚点链在这种用法下要多一层推理。而 `_StageLine._draw()` 按 `size.x` 算段数与
断口位置 ⇒ 尺寸变了必须显式 `queue_redraw()`，否则会拿旧宽度画（线比控件短一截）。

## 四、三种「向中间靠拢」（用户已指认 **C**）

同一句话可以画成三种完全不同的东西，`docs/img/bench-line-two-readings.png` 有对照：

| | 画法 | 30s（满） | 0s |
|---|---|---|---|
| A | 余段**留在两端**，缺口从中线向两端扩 | 完整一条 | 两段缩到两端、消失 |
| B | 两段**整体向中间平移**（长度固定 = 1/4 宽） | **两段各占 1/4，中间空** | 在中点合拢 |
| **C（已实装）** | 余段**留在中间**，缺口从两端向中间扩 | 完整一条 | 两段缩到中线、消失 |

**B 有硬伤**：满条时不是完整线 ⇒ 「平台边缘」这个身份在准备阶段一开场就丢了，
且从战斗切回准备时会有一次视觉跳变（完整线 → 两段短条）。不推荐。

**A 与 C 的差别只在「余段贴哪一头」**：
- A：贴两端（线看起来「从中间裂开」）
- C：贴中线（线看起来「两端断掉、往中间收」）

**用户 2026-11-08 选 C。** 理由记在这一版里：中线是面板的对称轴，收缩的两头
**同时**朝它走 —— 读作「两端一起被吃掉」；A 则是「中间先裂一道缝」，
在深色星空上反而更像渲染缺陷。

`_StageLine` 的实现（C）：

```gdscript
var half := w * 0.5 * r                                  # r = 剩余比例
_span(w * 0.5 - half, w * 0.5 + half, w, col, 0.95)      # 一整段，居中
# 读条头贴在段的两端（即 w/2 ± half），不是控件两端
```

⚠️ 从 A 换 C 只改了这三处（亮段坐标 + 两个读条头的 x）。`_span()` 的 3% 渐隐
按**全宽**的两端算，所以 r 接近 1 时亮段碰到控件两端仍会柔和渐隐（正确）；
r 变小时亮段退到中间，两端就是**硬切**的断口（也无须改）。

## 五、实机实测（1920×1080 设计画布，窗口 2048×1152）

> ⚠️ **下表是 A 版（余段贴两端）的数据**，端点坐标在 C 版下不适用
> （C 的亮段是 `w/2 ± half`）。留着是因为它验证过三件事，与画法无关：
> ① 推送链路通且在递减；② 暗轨 0.30 的调色结论；③ 读秒色的 ΔG=34。
> 数值本身别再拿来做 A 的回归基线。

探针冻结主控后手动喂读数，逐态截图量像素。**量的是设计像素**（截图按 1.0667 换算回去）。

| 状态 | 理论端点 | 实测亮段（设计 px） | 判定 |
|---|---|---|---|
| 不读秒 `ratio=-1` | 0 ~ 1200 | 单段 384 ~ 1535 | ✅ 完整线 |
| 满条 `30/30` | 0 ~ 1200 | 单段 372 ~ 1547 | ✅ 两段在中点接成整条 |
| `15/30` | 0~300 / 900~1200 | **372~661 / 1258~1547** | ✅ 缺口 661~1258，居中对称 |
| `4/30` | 0~80 / 1120~1200 | **373~441 / 1478~1546** | ✅ 同上 |
| `0.6/30` | 0~12 / 1188~1200 | 370~372 / 1547~1549 | ✅ 只剩读条头 |

（端点比理论值内缩 ~12px 是两端 3% 渐隐 + 抗锯齿，非误差。）

**真实链路**（不手动设值，接回 `hud.tick_stage` 跑 90 帧）：
`time_left = 29.10/30.0` ⇒ `ratio = 0.970`，`hot = false`，`phase = 0`。
⇒ 推送链路通，且在递减。

### 两个调色决定（都是实测定下来的）

**① 暗轨 alpha 0.16 → 0.30。**
0.16 时缺口处实测 RGB ≈ (84, 92, 85) —— 和背景几乎同色，而且 **G 通道比 R 还高**
（这个游戏的星空背景偏青灰）。

但更关键的是 0.30 之后实测 (105, 105, 83)：R 与 G 拉平，读作**暖灰轨道**，
不再是「青绿色尾巴」。**低于 0.25 会被背景的 G 通道压过去，读成色偏 bug。**

**② 读秒色 `(1.0, 0.78, 0.41)` → `(1.0, 0.62, 0.30)`。**
前一版叠在星空上肉眼分不出来（实测金色 (211,169,71) vs 读秒色 (211,170,72)，ΔG 只有 1）。
现在读秒段实测 (203,135,74)，**ΔG = 34**，一眼能辨。
取橙不取红：红在这个游戏里已被「战败 / 危险」占用，读秒只是「快没时间了」。

⚠️ 顶条的环形倒计时**不随剩余时间变色**（恒为青蓝），所以这里没有可对齐的
既有语汇 —— 读秒变橙是新增的。5 秒这个阈值是**跟音频对齐**的
（`EveAudio.play_countdown` 的「最后 5 秒」提示音就是按它分档）。
视觉与听觉必须是同一条线，否则会出现「线已经变橙但一声没响」。

## 六、边界

- **出售态**（`set_selling(true)`）：整块变橙，读条层 `visible = false`。
  那会儿金线读起来只是干扰信息。
- **暂停**：`_process` 里 `_paused` 早退 ⇒ `tick_stage` 不跑 ⇒ 读条停住。
  这与「暂停 = 整个推进停摆」的口径一致。
- **移动端 / 紧凑布局**：`RECT_BENCH` 会被重排 ⇒ `resized` 触发
  `_sync_stage_line()`，读条跟着变宽。无需额外处理。

## 八、验收（交给用户跑）

- 进准备阶段：金线应从**满条**开始，随时间**匀速**从两端往中间收（C 画法）；
  顶条数字与缺口进展一致。
- 顶条 5 秒内：金线转橙。
- 点「开战」：金线**立刻**回到完整一条（不应残留半截）。
- 新手模式（不限时）：整局金线恒为完整一条，不收缩。
- 拖船进出售区：读条层隐藏；取消出售后恢复。
- 收缩到只剩一小截时：亮段应停在**屏幕正中**，不是贴着左右两端（这一条区分 A/C）。
