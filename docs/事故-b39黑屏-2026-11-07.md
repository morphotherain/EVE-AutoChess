# 事故：b39 热更让老客户端黑屏（2026-11-07）

> 一次典型的「热更架构约束被无意打破」事故。
> **影响面**：所有已装 b38 及以前完整包的客户端（Windows + Android）。
> **持续**：20:12（b39 上线）→ 21:20（回滚清单）≈ 68 分钟。
> **后果**：黑屏，且因为黑屏连上报都跑不到 —— 我们一度什么现场都没有。

---

## 一、现场

21:16 用户转来玩家反馈：「Windows 报黑屏，偶尔遇到」。
21:17 查 `/var/lib/eve-reports/`：**只有 1 条**，是部署时的 `selftest`，没有任何玩家报告。

也就是说：**玩家在黑屏，而我们收不到任何东西**。先得搞清楚「为什么一条都没有」。

## 二、第一个发现：上报通道对现有玩家完全无效

| | 玩家手上的完整包 | 当时的 pck |
|---|---|---|
| 版本 | 最晚 **b35**（2026-11-01） | b39（2026-11-07） |
| autoload | EveBoot / EveAiBridge / EveUpdater | 同上 **+ EveReport** |

`EveReport` 是 b39 才加的 autoload，而 b39 只以 hotfix pck 形式下发。
`ProjectSettings.load_resource_pack()` **只把 pck 的文件系统叠到 `res://`，
不重读 project.binary、不重新注册 autoload** —— autoload 列表在引擎启动那一刻就定死了。

⇒ 玩家挂上 b39 的 pck 后，脚本全是新的，但 `EveReport` 这个节点**从来不会被创建**。
崩溃上报、手动点版本号反馈，两条路都是死的。

**这一步已经足够解释「零上报」**，但还没解释「为什么会黑屏」。
继续查的时候，才挖出真正致命的那一条。

## 三、真正的根因：两条，都是「跨 pck 边界」

### 根因一：裸引用一个只存在于新包里的 autoload 名（编译期）

`eve_main_menu.gd` 里有一行：

```gdscript
EveReport.open_feedback()
```

老客户端的 autoload 注册表里没有 `EveReport` 这个名字。GDScript 对 autoload
标识符是**编译期**解析的 ⇒ 直接

```
SCRIPT ERROR: Parse Error: Identifier "EveReport" not declared in the current scope.
ERROR: Failed to load script "res://scripts/eve_main_menu.gd" with error "Parse error".
```

⇒ 主菜单脚本**整个加载失败** ⇒ 场景没有脚本 ⇒ **黑屏**。

> 复现方式（`project.godot` 里删掉 `EveReport=` 那行，然后 `--headless --import`）：
> 上面两行原样出现。这条实验是整次排查的转折点。

### 根因二：访问 autoload 的「新增成员」（运行期）

`_wire_updater()` 里直接写：

```gdscript
EveUpdater.update_available.is_connected(...)
EveUpdater.download_finished.connect(...)
EveUpdater.pending_update.is_empty()
```

这三样都是 2026-11-07 才加的。而 `EveUpdater` **在 `_try_mount()` 之前就实例化了**
（autoload 按 `project.godot` 顺序建，`EveBoot` → `EveAiBridge` → `EveUpdater`），
所以它的脚本**永远是基础包里的老版本**。

⇒ 老客户端上这些成员不存在 ⇒ 运行时 `Invalid get index 'update_available'`
⇒ `_ready()` 在这一行中断 ⇒ 界面只建了一半。

**注意这两条的性质不同**：
- 根因一是**编译期**，整个脚本不加载，直接全黑；
- 根因二是**运行期**，`_ready()` 中断，界面残缺。

## 四、为什么当时没发现

1. **发版时只验证了服务器能下发**，没验证客户端挂载后能不能起来。
   前一次「上报通道上线」也是这样 —— 只测了服务器能收，没测客户端会不会发。
2. **热更包没有「老客户端兼容性」检查**。`export_presets.cfg` 能保证包的内容，
   但没有任何东西约束「这份包挂到上一版客户端上会怎样」。
3. **自愈机制掩盖了问题的严重性**。`EveUpdater` 有「连续 3 次没进主菜单就删包回退」，
   所以理论上玩家重启 3 次能自己好 —— 这让事故看起来像「偶尔黑屏」，
   而不是「所有人都中招」。玩家反馈里那句「**偶尔遇到**」正是这么来的：
   他重启几次就好了，以为是偶发。

## 六、修复

| 文件 | 改动 |
|---|---|
| `project.godot` | **移除** `EveReport` autoload |
| `scripts/core/eve_report.gd` | 重写为「由主菜单创建」的普通 Node；不再读 `EveBoot` 的新字段；新增心跳与三态存活标记 |
| `scripts/eve_main_menu.gd` | 删掉 `EveReport.xxx` 裸引用；新增 `_ensure_reporter()` / `_boot_reporter()`；新增 `_up_has()` 并给 `_wire_updater()` 加闸门 |
| `tools/check_hotfix_safe.py` | **新增**：发版前比对 autoload 基线，新增即拒绝 |
| `tools/hotfix_baseline.txt` | **新增**：基线 = 玩家手上完整包的 autoload 列表 |
| `tools/verify_report.gd` | **新增**：20 条验收，静态扫源码 + 运行时探行为 |
| `tools/publish_hotfix.sh` | 在**导出之前**插入兼容性闸门 |

### 关键设计：为什么上报宿主放在主菜单

```
autoload 注册表  ← 引擎启动时定死，热更改不了   ⇒ 放这里的东西热更永远改不动
被 pck 覆盖的脚本 ← 主菜单、战斗场景……          ⇒ 放这里的东西热更能改
```

把宿主从 autoload 挪到主菜单之后，**上报逻辑本身也能通过热更更新了** ——
这正是最初想要的效果，只是第一版走错了路。

## 七、防护：把教训变成可执行的闸门

`tools/check_hotfix_safe.py` 做两件事：

1. 比对 `project.godot` 的 autoload 与 `tools/hotfix_baseline.txt`
   （= 上一次发完整包时的列表）。**有新增就直接拒绝发布**，并提示
   「要么把功能挪到被场景加载的脚本里，要么别发 hotfix」。
2. 就算没有新增，也再跑一次全工程解析，抓「代码引用了不存在的名字」这类写法。

它挂在 `publish_hotfix.sh` 的**导出之前** —— 不合规就不浪费一次导出。

反向验证过：临时注入一个假 autoload `EveTestGhost`，闸门报错并 `exit 1`。
**一个永远返回「通过」的闸门等于没有**，所以这一步必须做。

`tools/verify_report.gd` 的 20 条里，有三条是**静态扫源码**的：
这类错误在编译期就发生，运行时根本跑不到，只能扫文本。

> 踩到的小坑：初版静态检查直接 `contains("EveReport.")`，
> 但源码注释里大段写着「以前是 `EveReport.open_feedback()`」讲事故经过
> ⇒ 检查永远红。必须**先剥注释**再判。

## 八、给黑屏玩家的自救办法

b39 的包已经在他们本地了（`user://update.pck`）。两条路：

1. **等自愈（推荐）**：连续启动 **3 次**。`EveUpdater` 每次挂载前把
   `boot_fail` +1，主菜单起不来就清不掉，第 3 次会自动删包回退到本地版本。
2. **手动删**：删掉
   `%APPDATA%\Godot\app_userdata\EVE 自走棋\update.pck`
   （Android 是 `Android/data/<包名>/files/update.pck`），重启游戏。

自愈/删包之后，下次启动会正常拉到 **b40**（已修复），从此不会再黑。

## 九、必须记住的三条

1. **autoload 列表和 `class_name` 注册表都属于「引擎启动时才生效」的东西，
   热更 pck 一律改不了。** 新增它们必须发完整包。
2. **任何跨越 pck 边界的访问都要做存在性检查。**
   automload 节点是老脚本、调用方是新脚本，两者的成员集合永远不同步。
3. **发版验证不能只验「服务器能不能发出去」，要验「客户端能不能起来」。**
   这次事故的 68 分钟里，我们连一句玩家的日志都没有 —— 因为黑屏时
   连上报节点都创建不出来。**上报通道本身也是这个 bug 的受害者。**
